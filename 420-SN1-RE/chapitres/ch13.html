Problème d'ouverture

Une équipe remet son rapport sur une station météo. En le lisant, on découvre trois choses :

  • deux mesures manquantes ont été remplacées par 20 °C « pour que la courbe soit plus belle »;
  • la fonction qui calcule l'écart type vient d'un forum, sans aucune mention de la source;
  • une autre fonction a été produite par un assistant d'IA. Elle s'exécute sans erreur, mais elle donne un mauvais résultat, et personne ne l'a testée.

Le programme fonctionne. Le rapport, lui, ne vaut plus rien : on ne peut faire confiance ni aux données, ni au code. Ce dernier chapitre porte sur ce qui rend un travail scientifique fiable : une démarche complète, des données intègres, des sources citées et un usage vérifié de l'IA.

L'intégrité des données

En sciences, les données sont des preuves. Les modifier pour obtenir le résultat espéré, même un peu, c'est de la falsification : la faute la plus grave en recherche. Mais les données réelles sont imparfaites : mesures manquantes, codes d'erreur des capteurs, valeurs impossibles. Il faut donc les nettoyer, de façon honnête et traçable.

Cinq règles :

  1. Ne jamais modifier les données brutes. Le fichier original reste intact; le programme construit une nouvelle liste nettoyée.
  2. Décider des règles de rejet avant de regarder les résultats, et les écrire dans le code : « valeurs hors de −40 à 50 °C rejetées », pas « j'ai enlevé ce qui semblait bizarre ».
  3. Compter et rapporter ce qui a été rejeté, et pourquoi.
  4. Ne jamais inventer une valeur. Une mesure manquante reste manquante. Si une méthode exige de la remplacer, on le dit clairement dans le rapport.
  5. Rendre le traitement reproductible : relancer le programme sur les données brutes doit redonner exactement le même résultat.

Le capteur a produit −999, un code d'erreur, et 85.0 °C, une valeur impossible un jour de novembre. Les deux sont rejetés par la même règle, écrite dans le code. Le rapport dit combien de mesures ont été rejetées : le lecteur peut juger.

Piège : rejeter ce qui dérange

Une mesure qui s'éloigne du modèle n'est pas fausse pour autant : c'est peut-être une découverte, ou le signe que le modèle est mauvais. On ne rejette une mesure que selon une règle fixée d'avance (plage physique, code d'erreur, critère d'aberrance comme au chapitre 8), jamais parce qu'elle gâche le résultat.

Citer le code

Réutiliser du code est normal : c'est ainsi que travaillent les programmeurs. Le présenter comme le tien, par contre, c'est du plagiat, au même titre que copier un texte. La politique d'évaluation du cégep le traite de la même façon.

Tout code qui ne vient ni de toi ni des notes du cours (un livre, un site, un forum, un collègue, une IA) se cite dans un commentaire, juste avant le code emprunté :

# Source : réponse de l'utilisateur « mathfan42 » sur un forum de programmation,
#          fil « Python sample standard deviation », consulté le 2026-11-20.
#          https://forum.exemple.org/q/15389768   (exemple fictif)
# Modifications : noms de variables traduits; ajout du cas d'une liste
#                 de moins de deux mesures.
def ecart_type(mesures):
    ...

Une bonne citation répond à quatre questions :

Question Exemple
Qui ou quoi? l'auteur, le site, le livre, l'outil d'IA
Où? le lien, ou la référence complète
Quand? la date de consultation : les pages changent
Qu'as-tu changé? ce que tu as adapté, ajouté ou corrigé

Citer ne te dispense pas de comprendre. Tu restes responsable de chaque ligne que tu remets, citée ou non.

Les licences

Le code publié en ligne a souvent une licence (MIT, GPL, Creative Commons…) qui dit comment on peut le réutiliser. Pour un travail scolaire, la citation suffit presque toujours. Dans un projet professionnel ou publié, la licence devient importante : vérifie-la.

L'IA générative : un outil à vérifier

Les assistants d'IA écrivent du code en quelques secondes. Ils sont utiles, et ils se trompent : ils produisent du code plausible, qui s'exécute souvent sans erreur, mais qui peut être faux. En sciences, un résultat faux qui a l'air juste est le pire des cas.

La règle du cours

Elle n'a pas changé depuis la première semaine (Politique sur l'IA) :

  • Permis : demander à l'IA d'expliquer une notion, un message d'erreur ou un exemple.
  • Non permis : lui faire écrire le code d'un exercice, d'un labo ou d'une évaluation.

Dans tes cours suivants et au travail, la règle sera différente : l'IA écrira peut-être une partie de ton code. Ce cours t'a donné ce qu'il faut pour la surveiller : planifier, faire une trace, tester, valider.

Vérifier le code d'une IA

Voici une fonction qu'un assistant d'IA a produite pour la demande « écris une fonction Python qui calcule l'écart type d'un échantillon de mesures ». Elle a l'air correcte. Teste-la sur un cas dont tu connais la réponse : l'écart type de 2, 4, 4, 4, 5, 5, 7, 9 vaut environ 2.138.

Le test échoue : la fonction divise par n au lieu de n − 1. C'est l'écart type d'une population, pas d'un échantillon (chapitre 8). L'erreur est subtile, l'IA ne l'a pas signalée, et le code s'exécute sans aucun message. Seul un test sur un cas connu la révèle.

Essaie-le

Corrige la fonction pour que le test passe. Ajoute ensuite un deuxième test : l'écart type de [10, 10, 10] doit valoir 0.

La même démarche s'applique à tout code que tu n'as pas écrit :

  1. Lis-le ligne par ligne. Une ligne que tu ne comprends pas est une ligne que tu ne peux pas remettre.
  2. Fais une trace sur un petit exemple.
  3. Teste-le sur des cas connus, et sur des cas limites : liste vide, une seule valeur, valeurs négatives, valeur égale au seuil.
  4. Valide le résultat : unités, ordre de grandeur, bon sens physique.

Déclarer l'usage de l'IA

Quand l'IA est permise, son usage se déclare comme une citation, avec en plus la requête utilisée et ce que tu as vérifié :

# Code initial produit par un assistant d'IA, le 2026-11-20.
# Requête : « écris une fonction Python qui calcule l'écart type d'un échantillon ».
# Vérification : testé sur [2, 4, 4, 4, 5, 5, 7, 9] (2.138) et [10, 10, 10] (0).
# Correction : division par n - 1 au lieu de n.

Pièges fréquents

  • Modifier la liste des données brutes pendant le nettoyage, au lieu d'en construire une nouvelle.
  • Rejeter une mesure parce qu'elle dérange le résultat, plutôt que selon une règle fixée d'avance.
  • Remplacer une valeur manquante par une valeur inventée, sans le dire.
  • Remettre du code emprunté sans le citer, ou du code qu'on ne peut pas expliquer.
  • Faire confiance à du code parce qu'il s'exécute sans erreur.

Exercice 13.6 — Révision : le volume d'une crue

À faire

Pendant une crue, on mesure le débit d'une rivière (m³/s) à des instants irréguliers (h). Avec NumPy, convertis les instants en secondes, puis calcule par la méthode des trapèzes le volume d'eau écoulé, en m³, dans volume. Garde aussi le débit maximal dans debit_max et l'instant où il survient, en heures, dans heure_max.

Exercice 13.7 — Révision : une culture de bactéries

À faire

Une culture de bactéries suit le modèle logistique : dN/dt = r N (1 − N/K), avec N₀ = 100 bactéries, r = 0.5 par heure et K = 10 000. Avec la méthode d'Euler et Δt = 0.01 h, trouve t_moitie, le premier instant où N atteint ou dépasse K/2. Calcule l'instant au pas i par round(i * dt, 10).

Valide ton résultat : la solution exacte vaut ln((K − N₀) / N₀) / r, soit environ 9.19 h.
